# 0014: A TypeScript file is the token source; one model, no CSS parser

Status: proposed (M2). The user chose the TypeScript source on 2026-11-26. An independent challenge runs before this record is accepted. Date: 2026-11-26.

## Context

- Tokens used to be written by hand in `packages/css/src/tokens.css`, `accents.css` and `options.css` (252 lines after ADR 0012; 240 token values in 38 rule blocks). Everything else was generated by parsing them:
  - `@monoline/css/dist/tokens.json`, the public export;
  - `packages/tokens/dist`: `tokens.json`, `tokens.css`, `figma-variables.json`, `tokens.d.ts` and `native.json`;
  - the contrast check.
- Four readers used to parse that CSS (audit `docs/audit/2026-current-state.md`, Tokens row). Earlier in M2 they became one parser, `parseSources()` in `packages/tokens/scripts/lib.ts`, which validates missing, circular, duplicate and invalid references.
- M2 (`docs/MISSION.md`) asks for one source of truth. It suggests evaluating DTCG JSON in `@monoline/tokens` as a source that generates CSS, TS and React Native values. Both CSS and DTCG were prototyped and measured (Options).
- The user's decision (2026-11-26): the source is a TypeScript file. It is not the CSS, and not DTCG JSON.

## Decision

`packages/tokens/src/tokens.ts` is the token source. It is plain, erasable TypeScript that Node runs directly, and `tsconfig.scripts.json` typechecks it.

- **Shape.** Each of the three CSS files is a list of items in output order:
  - `{comment}`: a comment on its own line;
  - `{selector, groups}`: a rule block, with an optional `note` above it. A group is `{note?, tokens}`, and a token is `'value'` or `['value', 'note']`;
  - `{raw}`: CSS kept as written. This holds the two `options.css` rules that style descendants (`[data-font] .display`, `[data-radius] .badge/.tag/.btn`), so `options.css` stays one file in the same rule order and `bundle.ts`, `check-layers.ts` and `check-motion.ts` are unchanged.

  `accents.css` is a table with one row of `[--accent, --accent-text, --accent-2, --on-accent]` per preset and theme. Every comment in today's CSS, contrast notes included, is in the model, and the generator writes it back out.
- **Type-checked references.** Values are CSS strings: a reference is `var(--name)`. A type at the end of the file collects every `var(--x)` in the model and every declared name. A reference to a name that is not declared fails `tsc`: `Type 'true' does not satisfy the expected type '"--foregrund"'`. A `ref()` helper typed against the name union was tried first. TypeScript cannot infer the names of an object whose values call a function typed on those same names (TS2502, TS7022, TS2456), so the helper would need a hand-kept list of every name. The type-level check needs none.
- **One model, no parser.** `sources()` in `packages/tokens/scripts/lib.ts` reads the model and returns the same `{base, themes, accents, options}` the parser did. Every output reads it:
  - the token CSS (`cssFiles()`);
  - `tokens.json`, `tokens.css`, Figma variables, `tokens.d.ts` and `native.json`;
  - `@monoline/css/dist/tokens.json` (`packages/css/scripts/build.ts`);
  - the contrast check (`check.ts`).

  `parseSources()` is deleted. `cssBlocks()` stays as a plain CSS reader, used for two things only: the round-trip test (the generated CSS reads back to the model's blocks and declarations) and the `prefers-contrast: more` block of `utilities.css`.
- **Generated CSS.** `npm run tokens` writes `packages/css/src/tokens.css`, `accents.css` and `options.css`, each under the header `/* Generated from packages/tokens/src/tokens.ts by \`npm run tokens\`. Do not edit: change that file and run \`npm run tokens\`. */`. The files are committed because the stylesheets, the bundle and the docs load them.
  - **Layout.** The generator owns it: one declaration per line, a blank line between groups and between rules, a token's note on its line, other notes above, `accents.css` one line per rule. The previous hand alignment could not be derived by any rule. Some groups were padded and some were not, and some declarations shared a line, so reproducing it would have meant storing layout in the source. The layout change was made once, alone, in `5ecadfb`, which is in `.git-blame-ignore-revs`.
  - **Staleness.** `npm run check` (`packages/css/scripts/check.ts`) and `npm run test:tokens` fail when a committed CSS file differs from what the source generates. CI diffs the three files after `npm run tokens`.

Validation runs on the model (`sources()`), and the build stops with the file, block and token:

| Class | Rule | Caught by |
|---|---|---|
| Missing reference | every token resolves in every theme × (no accent + 8 accents) × font, radius and density combination (3 × 9 × 27 = 729 environments) | `tsc` (the type check) and `sources()`: `tokens.css :root: --a uses undefined token --nope (theme warm)` |
| Cycle | a real cycle check (the resolution stack), also cycles that only close when a theme or accent layer applies | `sources()`: `accents.css [data-accent="x"][data-theme="dark"]: reference cycle --a -> --accent -> --a (theme dark, accent x)` |
| Duplicate | the same token twice in one layer. Within one group it is a repeated object key, so `tsc` refuses it (TS1117). Across groups or blocks of one layer (e.g. `:root` and `:root, [data-theme]`), the build refuses it. A theme or accent overriding a base token is the cascade and is allowed. | `tsc`, and `sources()`: `--a is declared twice in this layer; keep one` |
| Invalid reference | `var(` must be exactly `var(--name)`. Refused: malformed, not a custom property (`var(color)`), or with a fallback (`var(--b, red)`, which would hide a missing token). | `sources()`. A fallback also fails `tsc`, since `--b, red` is not a declared name. |
| Selector | a list that starts with `:root` and otherwise holds bare attributes (ADR 0012) is the base layer; any other `tokens.css` selector is refused, as is an `options.css` token block without one `[data-kind="value"]` selector | `sources()`: `tokens.css: unexpected selector ".card"` |

Contrast (`contrastChecks`, run by `npm run check`) resolves the model: 126 checks over 3 themes × (no accent + 8 accents), the code colours on `--surface`, and the `prefers-contrast: more` mixes. All pass.

## Options considered

All three were built against the same tokens: A is the CSS with the one parser, B was a prototype, and C is now the source.

### Option A: CSS is the source

Hand-written CSS → one parser (validates) → every output.

| Dimension | Assessment |
|---|---|
| Source size | 252 lines in 3 files; a new theme colour is 3 lines |
| Contributor workflow | edit `tokens.css`, run `npm run tokens` |
| Comments | kept where written |
| Typos in references | caught when `npm run tokens` or `npm run check` runs, not by the editor or `tsc` |
| Second path | the parser is a second representation of the cascade, rebuilt from text |

**Pros:** smallest source; no generated source files; contributors edit what ships.
**Cons:** the model is rebuilt from text on every run; nothing typed; validation is the only guard.

### Option B: DTCG JSON is the source (prototype, rejected)

`monoline.tokens.json` → `to-css.ts` → the three CSS files → the same parser and outputs. It was measured against the files at the time (before ADR 0012 moved the derived tokens):

| | tokens.css | accents.css | options.css |
|---|---|---|---|
| Lines, real → generated | 172 → 136 | 37 → 170 | 26 → 53 |
| Generated lines found verbatim in the real file | 54 | 25 | 21 |
| Tokens per block, selectors, every declaration | equal | equal | equal |
| Comment text kept | 33 of 33 | 1 of 1 | 2 of 2 |
| `tokens.json` built through the one parser | identical | | |

- The source was 1,338 lines of JSON for 232 lines of CSS (5.8×). A new colour was 12 lines.
- Values stayed CSS strings, because DTCG has no expressions: 17 values embed references inside `color-mix()`, `calc()`, a gradient or a shorthand, and 5 are `clamp()`.
- The layers (base, theme, accent, option) lived in `$extensions`, which no tool reads.
- DTCG gaps in the then `dist/tokens.json` (240 values):
  - 23 hold `var()` where DTCG wants an alias;
  - 8 have `$type: color` on a `var()` or `color-mix()` value;
  - 44 have no `$type`;
  - 46 dimensions are strings rather than `{value, unit}` objects;
  - themes and accents are top-level groups, because DTCG has no modes.

  These are the same under every option: they come from the CSS semantics, not from the source format.

**Pros:** a design tool that writes DTCG could be the editor.
**Cons:** 5.8 times the source, still CSS strings, and generated CSS. Contributors edit two formats.
**Status:** rejected by the user; the prototype is deleted.

### Option C: a TypeScript file is the source (chosen)

`src/tokens.ts` → `sources()` (validates) → the three CSS files and every output. No parser.

| Dimension | Assessment |
|---|---|
| Source size | 532 lines for 308 lines of generated CSS. The data itself is about 480 lines, with one token per line as in the CSS; the rest is the format description and the 21-line type check. A new theme colour is 3 lines, one per theme block, as in A. |
| Pipeline code | `blocks()` 13 lines, `sources()` 22, `cssFiles()` 40, the type check 21. `parseSources()` and the DTCG prototype (`to-css.ts`, `from-css.ts`, 1,338-line JSON) are deleted. |
| Typos in references | fail `tsc` (`npm run typecheck:scripts`, part of `npm run check`) with the token's name, and in the editor |
| Comments | every comment is a `note` or `comment` in the model and is written back to the CSS. Only their position follows the generator's rule. |
| Contributor workflow | edit `src/tokens.ts`, run `npm run tokens`, commit the TS, the three CSS files and `dist/` together. The CSS files say "Do not edit" in their header. |
| Outputs | byte-identical (`cmp`): `@monoline/css/dist/tokens.json`, `monoline.min.css` and the five `packages/tokens/dist` files. `monoline.css` and `core.css` differ only by whitespace and the generated header. |

**Pros:** one model that every output reads, so no text is parsed back into tokens. References are checked by the type checker. The source is the same language as the rest of the repo, with no new tool.
**Cons:** the CSS that ships is generated and committed, so a contributor can still edit it by mistake. The staleness check catches that, and the header says so. The layout of the CSS is no longer hand-tuned. Values stay CSS strings, the same as in A and B.

## Trade-off analysis

- **A vs C.** C keeps A's semantics (CSS values, the same cascade) and replaces the parser with the model it was rebuilding. That removes a second path, and moves reference errors from the build to the type checker. The cost is generated files in `packages/css/src` and a TS file twice the CSS's length.
- **B vs C.** B moved the edit point to a format with no expressions and no layers, so it added length without adding meaning. C adds types, which catch the most common token mistake: a misspelt reference.

## Consequences

- `packages/css/src/tokens.css`, `accents.css` and `options.css` are generated. Hand edits fail `npm run check`, `npm run test:tokens` and the CI diff.
- Adding a token: edit `packages/tokens/src/tokens.ts`, run `npm run tokens`, commit everything it regenerates. AGENTS.md, DESIGN.md and `packages/tokens/README.md` describe this.
- `packages/css/scripts` imports `packages/tokens/scripts/lib.ts`, which imports `packages/tokens/src/tokens.ts`. Only repo scripts do; `@monoline/css`'s published files are unchanged. `@monoline/tokens` (private) lists `src` in `files`.
- The non-token `options.css` rules are CSS inside the TS file (`{raw}`). They are not validated as tokens. A third such rule should get a stylesheet of its own rather than more raw CSS in the model.
- Changes from earlier in M2 are kept:
  - `dist/native.json`;
  - `--heading-1/2` filed as type tokens;
  - the 126-check contrast run on resolved values;
  - the validation classes.
- DTCG stays an output (`dist/tokens.json`), with the gaps listed under B.
